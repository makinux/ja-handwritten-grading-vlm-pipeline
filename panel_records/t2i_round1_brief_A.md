## プロジェクト文脈(自己完結の前提情報)

- 目的: 日本語手書き答案の自動採点VLMを開発する企業プロジェクト。その学習/評価用合成データセット(答案画像)を作るパイプラインの設計。
- 現行レンダラ(m3_render.py): PIL+フォントで答案ページを描画。設計原則は (1) label-by-construction(正解テキストが構成的に確定)、(2) 文字単位bbox GT(ステップbbox・誤りスパンbboxをピクセル座標で出力、位置報酬はbbox IoU)、(3) ペア生成原則(誤りあり/なしの双子でスタイル・ジッタ乱数列を完全共有)。
- 規模: Phase 0で1万サンプル、将来30万頁。
- ハードウェア制約: GMKtec EVO-X2(AMD Ryzen AI Max+ 395、Radeon 8060S iGPU、CUDAなし、128GBユニファイドメモリ)単機+予算ゼロ運用。Kaggle無料枠(T4×2、週30h)が代替。クラウドスポットは「予算確保後の条件付き」。LLM系の外部API(GPT等)は不使用方針。
- ユーザーが実行可能な検証規模: EVO-X2ローカル+Kaggle無料枠+高々数千円のクラウドスポット。反証条件はこの規模で実行可能なものにすること。

# 手書きレンダリングの T2I 化・FT 検討書(2026-08-17)

決定事項: 手書き風レンダリングの強化は **Qwen-Image 系(Apache-2.0)** で行う(ユーザー確定 2026-08-17)。商用 API(GPT Image 2 / Nano Banana)は日本語文字品質では最高水準だが、(1) 生成物を自社 VLM の学習に使うことが両社規約でグレー(競合モデル開発への出力利用禁止条項)、(2) hardware_plan の「外部 API 不使用」方針、の 2 点で不採用。

## 基本方式: プロンプト直接生成ではなく「グリフ保存スタイル変換」

プロンプトから答案全体を直接生成する方式は採らない。理由は設計原則との衝突:

| 設計原則(m3_render) | 直接生成での問題 |
|---|---|
| label-by-construction | 漢字崩れ・別字化が確率的に混入し GT が壊れる |
| 文字単位 bbox GT | 生成画像から bbox を回収できない |
| ペア生成原則(双子でスタイル共有) | 確率的生成で双子の同一性が崩れる |

代わりに **「フォント/グリフバンクでレンダリング → Qwen-Image-Edit で手書き風に変換」** の 2 段構成とする。編集モデルは入力画像のグリフを条件として受け取るため、文字の正確性が構成的に担保されやすい。日本語での実証:

- Qwen-Image-Edit に「フォント画像→書道風変換」をさせると、直接生成より一字一字の精度が大幅に高く画数の多い漢字でもストローク保存(飯塚氏 zenn.dev/kota_iizuka/articles/33219ebb8aff99)
- フォントレンダ画像入力で日本語破綻を回避、縦書き対応。ComfyUI 用 Text Renderer ノード公開済み(きしだ氏 nowokay.hatenablog.com/entry/2026/01/05/110344)

使用モデル: **Qwen-Image-Edit-2511**(2025-12-26、Apache-2.0、GGUF/fp8 あり、ComfyUI ネイティブ対応、Lightning 4-step 蒸留 LoRA で約 10 倍速)。T2I 側は Qwen-Image-2512(手描き図形の生成に使う場合のみ)。Qwen-Image-2.0(2026-02 発表)はオープンウェイト化未確認のため対象外。

## 段階計画(予算ゼロ運用と整合)

### Stage B': グリフバンク・レンダラ(diffusion 不要・最優先)

m3_render の TODO「自前収集字形バンク」を **ETL 文字データベースの実筆グリフ**で実現する。フォントの代わりに実手書き字形を文字単位で合成配置する。

- **ETL 規約は 2025-03-28 改定で目的制限が撤廃され、商用含め無条件無料**("Use of Database is allowed for free."、禁止はデータ自体の再配布のみ。出典表記義務あり)etlcdb.db.aist.go.jp/download2/
- ETL9B: JIS 第 1 水準 2,965 字+ひらがな×200 筆者 → 筆者 ID を「書き手スタイル」として双子で共有すれば**ペア生成原則・bbox GT・label を完全保存**したまま実筆の字形多様性が入る
- 実グリフ合成配置は HTR 分野の定番手法(CASIA 孤立文字の行合成、PageNet 等)で学術的裏付けあり
- CPU で動くため EVO-X2 で 30 万頁レンダリングの現行計画と両立
- 弱点: 字間・ベースラインの不連続感、筆記の文脈依存(連綿・崩れ)がない、ETL は 1970-80 年代の丁寧な楷書寄りで現代答案の乱雑さと分布差

### Stage A: Edit-2511 ゼロショット変換 PoC(小規模・並行)

Stage B' 出力(またはフォント出力)を Edit-2511 で「手書き答案風に自然化」できるかの検証。2511 はコミュニティのスタイル変換 LoRA 群を本体統合済みでゼロショット性能が上がっている。

- 実行環境: EVO-X2 の iGPU では 20B diffusion は低速(分オーダー/枚)。**Kaggle T4 無料枠 + GGUF Q4(約 12GB)+ Lightning 4-step** が現実解。数十〜数百枚の PoC には十分
- 評価: 変換前後で (1) OCR/VLM 転記一致率(CER)、(2) 文字 bbox の位置ずれ、(3) 双子間のスタイル一致(同 seed・同設定で双子に適用)を測る。判定用 VLM はベースライン測定に使う Qwen3-VL(EVO-X2 上)を流用
- Go/No-Go: CER 劣化が閾値内(例: 追加誤読 <1%)かつ bbox ずれが許容内なら Stage C へ。ダメなら Stage B' 単独+撮像層強化で進む

### Stage C: Edit LoRA ファインチューニング(条件付き工程)

ゼロショットで「答案らしい乱雑さ」が不足する場合、control 付きペア学習で LoRA を作る。

- **ペアデータは自給できる**: 入力=フォントレンダ答案、出力=ETL グリフバンク合成答案(+撮像ノイズ)。同一テキスト・同一レイアウトで機械生成できるため、テキスト GT 既知のペアが無限に作れる。実務レンジは 500〜3,000 ペアで足りる見込み(スタイル系 Edit LoRA の相場)
- ツール: **musubi-tuner**(`--model_version edit-2511`、control 画像対応、Windows 可)または **DiffSynth-Studio**(2511 は `--zero_cond_t 1`)。初期設定: rank 16 / LR 5e-5(musubi)/ 1000〜3000 step
- ハード: fp8 + block swap で **24GB VRAM(RTX 4090 級)+ RAM 64GB** が学習可能ライン。EVO-X2 では不可、Kaggle T4 も 20B には不足 → **GRPO と同じ「予算確保後の条件付き工程」**。クラウドスポット(RunPod 等、2000 step ≈ 2〜3 時間 ≈ 数百〜千円台)で解凍可能な最安工程ではある
- 発展(任意): TUAT Kondate(一般 50 万円で商用可が明文化、文・数式・図の混在筆跡)を購入すれば「本物の連続筆記」を出力側に使う上位版 LoRA が作れる。これも予算確保後

### 手描き図形(グラフ・筆算・幾何図)

- 第一候補: **matplotlib xkcd 系の決定的線揺らぎ**(座標 GT・双子共有を完全保存、diffusion 不要)
- 第二候補: Qwen-Image-2512 で装飾的に生成(図形はラベルが意味レベルなので文字ほど忠実性リスクがない)。整った図→手書き風の ControlNet 変換は確立前例がなく要自前検証
- 数式手書きデータ(CROHME / MathWriting)は **CC BY-NC-SA のため商用出口がある本件では学習素材に使わない**

## レンダリング統合アーキテクチャ: 回答領域パッチ方式(ComfyUI API)

ETL-FT 済み(または ゼロショット)の Edit-2511 を、**回答領域のみ**に適用する。問題文は印刷フォントのまま残す(実試験は問題=印刷・回答=手書きなのでリアリズムもむしろ向上する)。

```
m3_render(改)
  ├─ 問題文: フォント描画(現行のまま)
  └─ 回答領域: グリフバンク/フォントでパッチ描画 + パッチ内文字bbox
        ↓ PNG + メタデータ(パッチのページ内オフセット)
ComfyUI (headless, --listen) へ HTTP POST /prompt
  workflow: LoadImage → Edit-2511 (+ETL-FT LoRA + Lightning 4-step)
            → KSampler(seed=pair_id 由来で固定) → SaveImage
        ↓ 手書き化パッチ
合成: ページに再貼付。ページ座標 = パッチオフセット + パッチ内bbox
        ↓
検品: OCR/VLM 転記照合(CER) + bboxドリフト検査 → 閾値超は棄却
```

- **座標保存の3層防御**: (1) ステップ(行)単位の小パッチに分割してドリフトを構造的に制限、(2) 変換前後パッチの位相相関で bbox を補正、(3) 検品ループで不一致棄却。報酬は bbox IoU ベースなので数 px のドリフトは元々許容範囲
- **リサイズ恒等化**: Edit-2511 は入力を約 1M ピクセルへ内部リサイズするため、パッチ寸法をモデル受理サイズ(16 の倍数・~1MP 以内)で描画し、座標変換を恒等にする
- **ペア生成原則**: 双子には同一 seed・同一 workflow を適用(seed は pair_id から導出=現行 style_from_pair と同じ流儀)
- **サーバ配置**: 常駐 API はローカル CUDA 機かクラウドスポット(RunPod 等)。Kaggle 無料枠は外部接続不可のため「パッチ一括アップロード→ノートブック内バッチ処理」形式にする(API 呼び出し層はバックエンド差し替え可能に作る)
- **順序**: FT 前にゼロショットで同じ配管を通す(Stage A)。API 呼び出し・座標帳簿・ドリフト補正・検品は FT と無関係に必要で、FT 後は LoRA ノードを 1 つ差すだけ。配管と座標保存性を先に検証してから GPU 費用を使う

## 検品ループ(全 Stage 共通)

diffusion を通した画像は必ず後段で検品する(2025-26 の合成データ研究で標準化したパターン: StyleText, SynthOCR-GEN, JSSODa):

1. VLM/OCR で転記 → GT と CER 照合、閾値超過サンプルは棄却
2. 変換前後の bbox 整合検査(誤りスパン bbox が変換後も誤り箇所を指すか)
3. 棄却率自体を KPI として記録(モデル・設定の比較指標になる)
