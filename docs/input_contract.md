# 入力契約(Input Contract)ドラフト

設計書 v2.1 §3 M4 の Phase 0 成果物。パネル確定所見:「運用時に模範解答・
採点基準が供給されるかを固定しなければ、ショートカットか正当な条件付けかを
区別できない」(A)/「M4(step_id 付き模範解答前提)と M5(answer_key のみ)で
供給前提が文書内で食い違っている」(B)への対応。

## 契約の定義

モデル入力は次の 2 条件を**両方**サポートし、評価は両条件を必ず併記する。

| 条件 | 入力 | 想定運用 |
|---|---|---|
| **C1: フル条件** | 答案画像+問題文+**模範解答(ステップ ID 付き)**+採点基準 | 学校・塾の定期試験(採点基準が事前に存在する) |
| **C2: 最小条件** | 答案画像+問題文+**解答キー(最終解のみ)**+採点基準 | M5 実データ・模範解答が整備されていない現場 |

訓練時は C1/C2 を **50/50 でランダムに切替**(条件ドロップアウト)し、
単一モデルで両運用に対応させる。アブレーション(§3 M6)の「模範解答除去」は
C2 が正式条件になったことで「タスク変更」ではなく「契約内の条件比較」になる。

## step_id の意味論(M4/M5 の食い違いの解消)

- `errors[].step_id` は「**入力として与えた模範解答のステップへの参照**」と定義する
  (=誤りが模範解答のどのステップからの逸脱かを指す)。
- **C2(模範解答なし)では step_id は null** とし、誤り位置は
  `bbox`+**転記行番号**(モデル自身の転記の何行目か)で指定する。
- したがって位置報酬は:C1 = bbox IoU+step_id 一致/C2 = bbox IoU+転記行番号一致。
- M5 の疑似ラベル・実データ評価は C2 契約で行う(answer_key のみで整合)。

## スキーマへの影響

- モデル出力 `errors[].step_id` を nullable に変更(C2 では null)。
- モデル出力に `errors[].transcript_line`(0-indexed 転記行番号)を追加。
- 合成データ側は両条件の GT を常に保持(step_id は生成時に既知、行番号は
  レンダラのステップ→行対応から機械的に導出可能)。
